# Deliverable matrix and completion gates

Use this reference to route the requested output and prevent partial delivery from being presented as a complete package.

| Request | Minimum output | Required audit |
|---|---|---|
| Innovation Discovery (broad direction, known problem or existing idea) | opportunity map, source-based problems, comparison of distinct routes, boundary notes, 0–3 recommended directions, exclusions and returns, minimal next check | compare L1/L2 before implementation; keep public evidence, hypotheses and applicant facts separate |
| Patent Validation (grounded technical route) | current opportunity record, coverage and one-column-per-publication matrix, combination and baseline checks, technical validation, independent review and unified candidate card with A–D grade | apply [candidate validation](candidate-validation.md); keep incomplete or invalidated handoffs pending; validation does not authorize drafting |
| Concept outline | confirmed technical problem, grounded candidate mechanism, expected effect, open design choices | source traceability and unresolved choices |
| Patent-point mining | grounded candidate cards, ranking only where alternatives exist, evidence gaps, split recommendation where applicable | problem and material check; no unsupported novelty claim |
| Prior-art search | source register, queries, feature matrix, exact citations, limitations | bibliographic and passage verification |
| Technical disclosure | title, field, background, problem, solution, effects and implementable embodiment, plus figures, alternatives or protection suggestions as requested or useful | compare mechanism and embodiments, mark pending facts and decisions, identify missing requested items |
| Claims | actual independent and dependent claim language with corresponding claim types where supported | support mapping, unity, dependencies and scope |
| Full application package | actual claims, specification, abstract, applicable drawings and abstract figure, plus requested forms or confirmed filing data | inventory and formal checks for each component, cross-document consistency |
| Office-action preparation | cited-reference feature map, response positions, amendments, evidence | distinguish novelty from inventive step |
| DOCX delivery | template-preserving editable files and change record | structural and visual QA where possible |
| Audit only | findings, severity, evidence, recommended corrections | no silent file mutation |

For a request to create a disclosure or filing text, or to change its technical spine, apply the [problem and material check](project-intake.md#problem-and-material-check) and assess the retained chain before drafting. If either is insufficient, report the blocked deliverable and return active discovery findings instead. A concept developed or changed in Explore also needs the [drafting handoff](idea-discovery.md#handoff-to-drafting). An audit or formal check of an existing draft can still proceed within scope.

## Closure report

For disclosures, identify protection suggestions and pending decisions as working material. For filing-oriented text, keep drafting notes outside the intended filing version and list missing mandatory components in the closure report. A list of figure descriptions records intended drawings. When drawings are requested, verify the drawing files themselves.

Always state requested deliverables, delivered files or sections, checks actually run, checks not run and why, unresolved evidence or legal uncertainty, and the next actionable step. “Drafted” is not “complete” unless the requested gates passed.

Drafted or revised patent text additionally reports: the field of art and classification used, the size of the term table, which terms were sourced from standards or literature, and any remaining `【术语待核】`. See [terminology.md](terminology.md). Filing-oriented deliverables also report the formal-checklist items that could not be checked. See [formal-checklist.md](formal-checklist.md).
