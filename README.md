# 中文发明专利写作技能

一个面向 Codex 的通用中文发明专利工作技能。它可以把论文、源代码、工程设计、实验记录、技术说明或已有专利草稿，整理为具有技术链条、证据边界和权利要求支撑的专利工作成果。

本技能适用于软件、人工智能、电子、声学、通信、制造、控制、医疗器械、材料、能源等技术领域，不局限于某一个科研项目。

想按场景了解这个技能能做什么、要准备哪些材料以及会收到什么，请看[功能与使用说明](USER_GUIDE.md)。

## 安装到 Codex

在终端执行以下命令，安装到当前用户的 Codex 技能目录。命令需要 Git。

Windows PowerShell

```powershell
git clone https://github.com/Nexelume/cn-invention-patent-writer.git "$env:USERPROFILE/.agents/skills/cn-invention-patent-writer"
```

macOS 或 Linux

```bash
git clone https://github.com/Nexelume/cn-invention-patent-writer.git "$HOME/.agents/skills/cn-invention-patent-writer"
```

只在一个项目使用时，在该项目根目录把命令中的目标路径改为 `.agents/skills/cn-invention-patent-writer`。安装后的 `SKILL.md` 应直接位于技能目录中。已有同名安装时，可先检查其来源和本地改动。通过上述命令安装且没有本地改动的版本，可进入技能目录运行 `git pull --ff-only` 更新。技能列表未显示时，重新打开 Codex。安装路径及技能调用方式见 [Codex 官方文档](https://developers.openai.com/codex/skills)。

## 第一次使用

在 Codex 打开材料所在的项目，从技能选择器选择 `cn-invention-patent-writer`，或在提示中写 `$cn-invention-patent-writer`。说明本次是探索、查新、起草、审查、修订还是成套交付，指出权威材料和输出要求。需要只读时，在请求中明确写出。

```text
使用 $cn-invention-patent-writer，仅依据当前目录的技术说明、实现代码和测试记录，
梳理候选发明构思。逐项说明输入、技术机制、输出和可核实的效果，
标出尚缺的证据和下一步需要确认的问题。请只读分析，先不写申请文件。
```

| 任务 | 建议提供的材料 | 本次应得到的结果 |
|---|---|---|
| 只有研究方向 | 一个方向就可开始；具体场景、失败样例或设计约束可一并提供 | 公开技术路线、候选问题、关键未知和最小验证建议；暂不起草 |
| 探索发明构思 | 设计说明、代码或试验记录 | 有材料支撑的候选技术链、取舍理由、证据缺口 |
| 查新或指定文献比对 | 拟保护的技术组合、对比文献或检索范围 | 查询记录、逐特征公开情况、原文位置及结论限制 |
| 起草交底书或权利要求 | 已选构思、可实施的设计细节、已有验证记录或拟议设计参数、模板（如有） | 可实施的交底草稿，或附有说明书支持位置的权利要求草稿 |
| 审查或定向修订 | 权威草稿、相关材料及允许修改的范围 | 可定位的问题清单，或针对指定问题的修订稿 |
| 成套交付或 Word 排版 | 已稳定的方案、模板、图件和已确认的申请信息 | 约定文件、检查结果和仍需确认的项目 |

检索公开文献需要可用的检索工具。只有摘要时，相关技术特征标为不确定。DOCX 版式验收需要可用的渲染工具，输出记录会列出实际完成的检查。

## 主要能力

- 扫描和整理项目材料，识别权威技术来源与证据缺口
- 判定发明所属技术领域，建立本领域术语表并全文统一使用专业术语
- 从论文、代码和工程资料中挖掘候选发明点
- 先[核查技术问题和材料](references/project-intake.md#problem-and-material-check)，再[筛选有依据的候选链](references/invention-selection.md#concept-gate-after-the-problem-and-material-check)。只有一条就评估这一条；一条也站不住就指出缺口，暂不起草
- 判断候选方案是否具有完整的技术链条和可保护性
- 设计单一发明构思，分析是否需要拆分多个申请
- 检索和比较中国及国际现有技术
- 编写中国发明专利技术交底书
- 起草权利要求书、说明书、摘要和实施例
- 设计方法、系统、设备和存储介质之间的对应保护形式
- 补充算法、数据结构、接口、参数、故障处理和反馈机制
- 绘制或规划专利附图及其文字对应关系
- 审查权利要求支持性、术语一致性、公式参数和逻辑闭环
- 按现行细则与指南逐项检查形式合规（说明书五部分、权项编号与引用规则、附图标记双向一致、摘要字数等）
- 按交底书、权利要求书、说明书、摘要或成套申请文本检查可机械判定的形式问题
- 用正常例和边界例复核核心机制，逐项定位拟保护特征的说明书依据
- 引用法条时锁定版本与条款级条号，避免沿用旧版细则编号
- 根据模板生成或修改 DOCX，并进行结构和版式检查
- 准备现有技术对比和审查意见答复思路

## 适用工作模式

### Explore：探索

先用当前材料与公开文献建立机会地图，从「缺什么能力、为什么有这个技术问题」走到「改变哪个机制、怎么实现」。开放探索通常比较三至五条有实质差异的路线，证据只支持更少时不凑数，最终最多推荐三条。发现重合或用户认为太窄时退回相应层次，保留原路线和理由。只有具备具体机制和可验证区别的候选才进入专利评估，探索不交付交底书。

候选进入专利验证后，机会档案记录五类来源的检索覆盖、逐篇特征比对、技术组合与简单替代、最小验证方案、独立反查和 A–D 准入结论。A 表示值得进入深度查新，B 表示继续构思，C 表示暂不建议申请，D 表示淘汰。详见[候选验证规则](references/candidate-validation.md)。

### Draft：起草

在技术问题明确、材料足以支持主线后，按授权撰写交底书、权利要求、说明书、摘要、实施例或其他指定材料。由探索转入起草时，先完成近邻比对、反向审查、最小验证与投入判断，并确认用户选择的主线。跨领域概念进入主线前，要说清它用什么输入、做什么操作、改变哪一个后续行为，以及去掉它会有什么可观察的差异。

### Audit：审查

只检查技术逻辑、现有技术区分度、权利要求支持性、术语一致性、公式参数、模板和交付质量，不擅自修改原文件。

### Revise：修订

在现有权威草稿上进行定向修改，保留重要修改内容和未解决问题。

### Package：成套交付

在发明构思稳定后，整合权利要求、说明书、摘要、附图和 DOCX 等交付物，并执行交叉一致性检查。

## 示例：输送线视觉剔除

沿用已有的虚构评测案例。若只知道「想给瓶盖检测加 AI」，先比较公开的缺陷识别、输送跟踪和剔除控制机制，再形成两个待核实的方向：出错的是缺陷识别，还是认对了却吹掉后一瓶？已有[编码器动态补偿方案](https://patents.google.com/patent/US9147326B2/en)（图 5，步骤 503–515）可作剔除时机的比对线索；不能直接把「用编码器做变速补偿」当作创新，也不能由此确定项目的错因。建议用少量可辨认的瓶体，在恒速和变速工况下逐瓶对照人工缺陷标签、识别结果、剔除指令和实际被吹掉的瓶。若识别结果正确却错剔，先查目标关联和剔除时机；若识别就错了，先查图像与识别条件。在分清问题前不写交底书。

原材料提到「反馈学习」，但 PLC 只确认收到指令，不能确认实际动作或哪一瓶被剔除；剔除后传感器也还只是备选。在明确实际结果怎样对应到具体瓶体，以及它会怎样影响后续数据或控制前，不把反馈学习列入发明主线。

## 基本技术链条

每个主要发明点都应尽量形成以下闭环：

```text
技术对象或状态
    → 数据或结构获取
    → 对象、时间、空间或过程关联
    → 区别于现有技术的处理机制
    → 决策量、控制量或可执行输出
    → 物理系统或信息系统动作
    → 直接技术效果
    → 反馈、记录或更新
```

对于 AI 发明，不能只写“使用人工智能提高准确率”。需要说明模型处理的具体对象、输入特征、输出含义、约束或风险机制、下游动作以及技术效果。

对于非 AI 发明，应直接说明其物理结构、信号处理、控制逻辑、数据处理过程或其他具体技术机制。

## 证据边界

本技能将技术陈述区分为：

- 已验证事实
- 现有技术事实
- 拟议实施方案
- 设计参数
- 验收标准
- 未知信息

没有实际实验或生产证据时，不会把目标值、设计值、仿真设想或论文计划写成已经取得的工业效果。例如，应写“验收标准为……”，而不能在没有证据时写成“现场应用后达到……”。

专利号、申请人、发明人、优先权信息、生产结果、测试结论和法律状态均不得根据文件名或推测生成。

## 领域术语规则

**必须使用发明所属技术领域的专业术语来描写和写作。** 术语关系到说明书是否清楚、完整（专利法第二十六条第三款），权利要求是否以说明书为依据并清楚、简要地限定保护范围（第二十六条第四款），以及后续修改是否超范围（第三十三条）。用词应准确指向本发明的技术对象，不能靠替换名称制造区别。

执行要点：

1. **先定领域，再定词**。先写清技术领域和可得的分类号（IPC/CPC 主组），词汇服从领域，而不是用词汇反推领域。
2. **只用本领域在论文、标准、产品规格书中真正使用的词**。不用通用同义词凑，不用顺手翻译，不借用相邻领域的说法。
3. **一个概念全文一个词**。标题、摘要、权利要求、说明书、实施例、附图必须一致；同义轮换是缺陷，不是变化。权利要求术语必须与说明书逐字一致。
4. **不自造术语**。为了让方案显得新颖而造词，会使保护范围不可确定。领域里没有对应的词，要么它不是技术特征，要么必须在说明书首次出现处明确定义并后文统一使用。
5. **不确定就标注，不用通用词顶替**。写候选术语并标 `【术语待核】`，给出 2–3 个备选及其来源，然后问用户。不得悄悄降级为"模块、装置、单元、数据、信息、处理"这类通用词。
6. **跨领域方案保留两套术语**（例如声学 + 机器学习、机械 + 控制），并在衔接处说明两套词指向同一对象，不能把其中一个领域压成另一个领域的说法。

术语来源优先级：国家标准/国际标准（GB/T、ISO、IEC 等，注明标准号与条款）→ 本领域权威教科书与综述 → 《专利审查指南》与同分类已授权专利 → 设备/软件官方规格书 → 行业术语表 → 通用词典（仅拼写参考，不用于确定含义）。

起草前先建**术语表**（中文术语｜英文对应｜缩写｜定义含单位｜首次出现位置｜禁用与易混词｜依据来源），交付前按表逐项校验。规则与校验清单见 `references/terminology.md`。

## 推荐输入

可以提供以下任意一种或多种材料：

- 论文、技术报告或项目说明
- 源代码和 README
- 系统架构、流程图或设计文档
- 实验记录、数据说明和结果表
- 已有技术交底书或专利模板
- 已公开专利、公开号或 PDF
- 现有权利要求和审查意见通知书

如材料来自一个项目目录，技能会先进行项目接入和材料分层，再决定进入探索、起草、审查、修订或成套交付模式。

## 完整性模型

一个完整的专利工作包包含六层：

1. **接入**：来源、管辖地、模板、术语和证据边界
2. **发明**：候选点、技术链条、现有技术、区别特征和技术效果
3. **证据**：检索来源、查询式、文献映射、实验来源和不确定性
4. **保护**：独立权利要求、从属权利要求、系统/设备/存储介质形式、支持性和单一性
5. **实现**：数据、接口、算法、参数、公式、故障处理、反馈和实施例
6. **交付与质检**：附图、DOCX、占位符检查、结构检查、版式检查和完成报告

缺失的层不会被自动编造，而会被明确标记为未完成，并给出最小补充动作。

## 形式自检脚本

在技能目录下运行 `scripts/check_form.py`。脚本需要 Python 3.10 或更新版本，仅使用标准库，支持 `.md`、`.txt` 和 `.docx`。示例中的文件名替换为实际路径。

```bash
python scripts/check_form.py draft.md
python scripts/check_form.py disclosure.md --kind disclosure
python scripts/check_form.py claims.docx --kind claims
python scripts/check_form.py application.docx --kind application --term-table terms.tsv --request-form request.md
python scripts/check_form.py --self-test
```

默认按可识别标题和章节判定类型。对于无标题的单件申请文件，可用 `--kind claims`、`--kind specification` 或 `--kind abstract` 指定。交底书中的实施步骤保留为正文，待确认事项按草稿提示处理。成套文本中的残留占位符会报错。检查结果按违规、待确认、未检查和通过报告。技术机制与实施例是否一致、证据是否真正支撑结论，由正文复核判断。

退出码 `0` 表示本次检查未发现 `FAIL`，`WARN` 和 `SKIP` 仍需逐项查看。退出码 `1` 表示检测到违规或执行错误，先查看报告或错误信息。机械检查的覆盖范围见 [形式检查清单](references/formal-checklist.md)。

## 重要限制

本技能用于技术整理、专利撰写辅助和证据审查，不构成专利代理、法律意见或正式申请。涉及申请策略、法律判断、侵权风险和最终提交时，应由具备相应资质的专利代理师或律师审核。
